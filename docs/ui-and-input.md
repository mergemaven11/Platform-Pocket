# UI and Input

Platform Pocket runs on a 240×135 display with a physical keyboard. That is a very different environment from a desktop or phone UI, so the interface is intentionally simple, explicit, and state-driven.

## 1. The screen is just pixels

There is no browser, HTML, CSS, or window manager.

The firmware draws directly to the Cardputer display with functions such as:

```cpp
M5Cardputer.Display.fillScreen(...);
M5Cardputer.Display.fillRect(...);
M5Cardputer.Display.drawFastHLine(...);
M5Cardputer.Display.setCursor(...);
M5Cardputer.Display.print(...);
```

That means every coordinate matters.

For a 240×135 display:

```text
(0,0) ----------------------> x
  |
  |
  |
  v
  y
```

The top-left corner is `(0, 0)`.

---

## 2. The shared visual system

The v0.5 UI uses a small set of reusable colors:

```cpp
uiBg
uiHeader
uiPanel
uiPanelAlt
uiAccent
uiText
uiMuted
uiSuccess
uiWarning
```

These names describe *purpose*, not a specific color.

For example, the accent may be cyan in one theme and green in another, but menu code still uses `uiAccent`.

That is the embedded equivalent of design tokens in a web application.

---

## 3. Shared screen chrome

Most screens follow this structure:

```text
+--------------------------------------+  y = 0
| HEADER                        BADGE |
+--------------------------------------+  y ≈ 20
|                                      |
|              CONTENT                 |
|                                      |
+--------------------------------------+  y ≈ 120
| FOOTER / CONTROLS                    |
+--------------------------------------+  y = 135
```

The important reusable functions are:

```cpp
drawHeader(...)
drawStatusHeader()
drawFooter(...)
```

This makes screens feel related and also keeps layout changes centralized.

---

## 4. Why selected panels are better than `>`

The old UI looked like this:

```text
> Network
  Security
  Docker
```

That works technically, but the user has to visually search for a one-character marker.

The refreshed UI uses filled selection areas and stronger contrast. The selection itself becomes the visual object.

This is especially important on a tiny screen where glanceability matters more than decorative detail.

---

## 5. Keyboard updates

The first line of input handling is:

```cpp
M5Cardputer.update();
```

This refreshes the Cardputer hardware state.

Without it, keyboard state can become stale.

The v0.5 code also pays attention to keyboard change events rather than continuously treating a held key as a new press.

Conceptually:

```text
No keyboard change
    -> do nothing

Keyboard changed + key pressed
    -> inspect key state
    -> route event to current screen
```

This makes menu navigation feel much less jumpy.

## 6. `KeysState`

The M5Cardputer library exposes a keyboard state structure.

Useful fields include:

```cpp
status.enter
status.esc
status.del
status.backspace
status.word
```

`status.word` contains printable characters generated by the physical keyboard.

That is what makes the terminal possible.

Example mental model:

```text
User presses H
     |
     v
keysState().word contains 'h'
     |
     v
terminalInput += 'h'
```

Modifier handling such as Shift is handled by the Cardputer keyboard library before characters appear in `word`.

---

## 7. Input means different things on different screens

This is one of the main reasons the state machine exists.

### Main menu

```text
;       previous item
.       next item
Enter   open section
```

### Wi-Fi results

```text
;       previous network
.       next network
Enter   details
Esc     section menu
```

### Terminal

```text
letters       add to command
Backspace     edit command
Enter         execute command
Esc           leave terminal
```

### Brightness

```text
;       decrease
.       increase
Esc     back
```

The same keyboard is reused, but the active `ScreenState` gives each event meaning.

## 8. Redraw strategy

A useful embedded rule is:

> Redraw when state changes, not just because `loop()` ran again.

Examples of useful redraw triggers:

- cursor moved
- terminal character changed
- command executed
- theme changed
- brightness changed
- Wi-Fi scan completed

This is easier on the display and makes behavior predictable.

---

## 9. Text truncation

The display is narrow, so long strings must be controlled.

The helper:

```cpp
truncateText(value, maxChars)
```

shortens text before drawing it.

Without truncation, long SSIDs or labels can run into badges, controls, or the edge of the display.

On embedded UIs, defensive text sizing is part of layout engineering.

---

## 10. Themes

`themeIndex` identifies the active palette.

`applyTheme()` then updates the semantic UI colors.

The current themes are:

1. Midnight Cyan
2. Matrix Green
3. Amber Ops

A theme screen changes `themeIndex`, applies the palette, and redraws.

Notice that the rest of the application does not need to know which theme is active. It only uses semantic colors.

## 11. Adding a new screen

If a new feature needs custom interaction, use this sequence:

1. add a value to `ScreenState`
2. create any state variables the screen needs
3. create `drawYourScreen()`
4. create the function that opens/initializes the screen
5. add an input branch in `loop()`
6. define where Escape/Back returns

Example:

```cpp
enum ScreenState
{
    // ...
    SCREEN_SIGNAL_MONITOR
};
```

Then:

```cpp
void drawSignalMonitor()
{
    drawHeader("SIGNAL MONITOR");
    // draw graph
    drawFooter("ESC Back");
}
```

The key question is always: **what state owns the keyboard right now?**
